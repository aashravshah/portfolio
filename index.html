Fleet Management Platform

Hospitals were losing hours to device failures the data could have flagged — if only it arrived in time.

The Problem

Device error logs are processed in batch — so biomedical and field service engineers see failures hours after they happen, long after the window to intervene has closed. Discovery with 20+ biomedical engineers made the real brief clear: this wasn't an analytics problem, it was a delivery problem. We're now migrating devices onto a real-time path, one at a time, toward an eventual streaming platform (case study 02).

Fig 01 — Batch and real-time coexisting today; devices migrating onto the API, one at a time
Key Decision — Keep Batch, or Migrate to Event-Triggered Transfer

Current: scheduled batch

Still the bulk path today. Logs collected on a schedule and processed in bulk — engineers see what already happened, informative for root cause but useless for prevention.

Migrating to: real-time API

Logs pushed the moment an error occurs, routed by issue type to the engineer who can act. Rolling out device-by-device alongside batch, toward a full streaming end-state.

IoT Streaming Platform

Moving 5TB+ of daily telemetry from batch to streaming — and everything that became possible once we did.

The Problem

At 5TB+/day, batch became the ceiling on everything: ML couldn't run on fresh data, remote diagnostics worked hours behind, and every new data source took ~4 months to onboard. The platform needed a new foundation — HIPAA-compliant throughout the migration, and open to products that didn't exist yet.

Fig 02 — Schema-validated ingest, hot/cold storage split, products read the layer they need
Key Decision — Amazon Kinesis vs. MSK (Kafka)

Considered: Amazon Kinesis

Lower setup overhead, but shard pricing gets unpredictable at 5TB+/day — and a short replay window limits how far back ML teams can reach.

Chosen: MSK (Kafka)

Predictable cost at scale, and log-based replay for any downstream consumer — keeping doors open for a roadmap that wasn't fully written yet.

Kafka over Kinesis wasn't about "better" in the abstract — it was about which constraints we could live with, and which doors had to stay open.

POC / MVP · AI-Powered Product

LLM-Powered Conversational Agent

Engineers were drowning in logs they didn't have time to read. The agent reads them, reasons over them, and answers back in plain language.

POC & MVP validated — production next
The Problem

Fast data still needed expert interpretation. Engineers spent hours reading logs and cross-referencing telemetry to reach conclusions — with no way to ask a follow-up. The data wasn't the bottleneck; the last mile of understanding was.

Fig 03 — Metadata-grounded agent, conversational in both directions
Key Decision — Generic Prompting vs. Metadata Fine-Tuning

Option A: generic prompting

Fast to prototype, but the model knows nothing about device types or failure history — generic outputs engineers won't trust.

Chosen: metadata fine-tuning

Grounded in device context and failure patterns, so it reasons about this device, this anomaly — specific enough to act on, and to ask follow-ups against.
